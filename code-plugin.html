스킬·MCP를 플러그인으로 묶기

흩어진 스킬과 자주 쓰는 MCP를 한 패키지로 묶어 팀에 배포합니다

이 페이지는 나만의 Skill 만들기를 먼저 읽고 오는 페이지입니다. 스킬을 한 번이라도 직접 만들어본 분에게, 여러 스킬과 도구를 한 묶음으로 만들어 팀에 뿌리는 방법을 설명합니다.

스킬, 그 다음

스킬 하나를 만들고 나면 마주치는 세 가지 벽

스킬 만드는 법은 익혔습니다. 그 다음에 막히는 자리들입니다

  • 벽 ① 나만 씁니다. 내 ~/.codex 환경에만 들어 있어서, 팀원에게 알려주려면 SKILL.md 본문을 일일이 복사해 붙여넣게 해야 합니다.
  • 벽 ② 손발이 없습니다. 스킬은 "어떻게 일할지"를 알지만, DART에서 데이터를 가져오거나 구글 시트에 결과를 쓰는 일은 못 합니다.
  • 벽 ③ 흩어져 있습니다. 하나의 시나리오에 스킬 두세 개가 같이 쓰여도, 깔 때는 하나씩 따로 깝니다. 누가 어떤 버전을 갖고 있는지 알기 어렵습니다.
INSIGHT

세 벽의 답은 같습니다. 스킬에 도구(MCP)를 붙이고, 관련된 것끼리 한 폴더로 묶고, 한 줄 명령으로 깔 수 있게 만든다. 그 묶음의 이름이 플러그인입니다.

MCP는 짝꿍

MCP가 뭔가요?

Codex에게 "이 도구를 쓸 수 있어"라고 알려주는 통로

스킬이 "이 일은 이렇게 해"라고 알려주는 매뉴얼이라면, MCP(Model Context Protocol)는 "이 도구를 쓸 수 있어"라고 연결해 주는 통로입니다. Codex가 DART에서 공시 데이터를 가져오거나, 구글 시트에 표를 쓰거나, 내 PC 폴더의 파일을 읽을 수 있게 만드는 길입니다.

스킬만 있을 때
📝 "이런 양식으로 정리해줘"는 안다
📝 그런데 데이터를 어디서 가져오지?
📝 결과를 어디에 저장하지?
→
스킬 + MCP가 만났을 때
🚀 DART MCP가 데이터를 가져온다
🚀 스킬이 우리 회사 양식대로 정리한다
🚀 구글 시트 MCP가 자동으로 올린다

자주 쓰는 MCP 예시

데이터 분야는 DART, OpenDart, Kensho(S&P), BigQuery, Snowflake가 자주 쓰입니다.
업무 도구 분야는 Google Sheets, Notion, Slack, Gmail, Calendar가 대표적입니다.
개발·파일 분야는 GitHub, Filesystem, Postgres, Playwright(브라우저 자동화)가 있습니다.
이 중 내가 자주 쓰는 두세 개를 골라 관련 스킬과 묶으면 그게 첫 플러그인입니다.

플러그인 해부

Codex 묶음 폴더 구조

필수는 config.toml 하나. 나머지는 묶고 싶은 만큼만 넣습니다

my-codex-bundle/ ├── config.toml # MCP 서버 선언 ([mcp_servers.*]) ├── AGENTS.md # 묶음 공통 지침 (어떻게 일할지) ├── skills/ # 묶고 싶은 스킬들 (skills.html에서 만든 SKILL.md) │ ├── report-format/ │ │ └── SKILL.md │ └── data-clean/ │ └── SKILL.md └── README.md # 받는 사람을 위한 설치·사용 안내

핵심은 스킬과 MCP가 한 묶음 안에 같이 들어간다는 점입니다. 스킬은 skills/ 하위에 폴더째 넣고, 묶음 공통 지침은 AGENTS.md에, MCP는 config.toml의 [mcp_servers.*]에서 선언합니다.

config.toml, MCP를 같이 묶는 자리

[mcp_servers.*] 블록 하나가 묶음의 핵심입니다

# report-suite — 분기 실적 보고서: DART 데이터 + 우리 회사 양식 [mcp_servers.dart] command = "npx" args = ["-y", "@opendart/mcp-server"] env = { DART_API_KEY = "${DART_API_KEY}" } [mcp_servers.google-sheets] command = "npx" args = ["-y", "@google/sheets-mcp"]

이 묶음을 깔면 skills/ 안의 스킬 두 개와 DART MCP, 구글 시트 MCP가 한꺼번에 설정됩니다. API 키 같은 비밀은 반드시 ${ENV_VAR} 형태로 적어 설치하는 사람의 환경에서 읽도록 합니다. config.toml에 직접 적으면 안 됩니다.

묶는 3단계
1
한 시나리오로 좁힌다
"무엇을 자동화하는 묶음인가"를 한 문장으로 정의

이미 만든 스킬을 다 넣고 싶은 유혹부터 끊습니다. 묶음의 정체성이 흐려지면 받는 사람이 무엇에 쓰는지 알 수 없습니다.

  • 한 문장 정의 예시. "DART 데이터로 분기 실적 보고서를 만든다"
  • 이 문장에 직접 쓰는 스킬만 skills/에 모읍니다.
  • 이 문장에 필요한 MCP만 config.toml의 [mcp_servers.*]에 적습니다.
  • "있으면 좋을 것 같은" 자산은 다음 버전(0.2.0)으로 미룹니다.
2
config.toml을 짠다
[mcp_servers.*] 블록이 핵심. 이름·버전은 폴더와 git이 맡는다

위 예시를 그대로 복사해 세 가지만 챙깁니다.

  • 묶음 이름. 폴더명을 영문 소문자와 하이픈으로 짓습니다(report-suite). 받는 사람이 보는 식별자가 됩니다.
  • 버전. Codex config.toml에는 버전 칸이 없으니 README 맨 윗줄이나 git 태그로 관리합니다. 스킬 본문이 바뀌면 0.1.1, MCP 구성이 바뀌면 0.2.0, 사용법이 바뀌면 1.0.0을 올립니다.
  • [mcp_servers.*]. 묶을 MCP마다 블록을 하나씩 두고 실행 명령을 적습니다. 환경 변수는 ${...} 형태로 빼둡니다.
3
깨끗한 환경에서 직접 깐다
"내 노트북에서만 동작하는 묶음"을 거른다

가장 흔한 실수는 본인 환경에 이미 깔려 있는 무언가에 의존하는 묶음을 만드는 일입니다. 깨끗한 디렉토리에서 직접 깔아보면 누락된 환경 변수, 잘못된 경로가 바로 드러납니다.

  • 깨끗한 디렉토리에서 git clone 후, config.toml의 [mcp_servers.*] 블록을 ~/.codex/config.toml에 붙이고 skills/를 등록합니다.
  • Codex를 새로 띄워 묶음 안의 스킬이 자동으로 호출되는지 확인합니다.
  • MCP가 붙었는지, 도구 목록에 노출되는지 확인합니다.
  • 안 되는 게 있으면 config.toml을 고치고 버전을 0.1.1로 올립니다.
팀에 뿌리기

배포 3가지 방법

팀 규모와 공개 범위에 따라 고릅니다

  • ① 로컬 폴더 공유. 사내 공유 드라이브에 폴더째 올려둡니다. 한두 명 작은 팀이거나 비공개 자산일 때 적합합니다.
  • ② GitHub 저장소. git clone 후 README의 설정 안내를 따라 config.toml을 병합합니다. 팀 단위 배포의 표준이고, 버전 관리와 이슈 추적이 같이 따라옵니다.
  • ③ 공개 템플릿 저장소. 외부 공개 자산입니다. 누구나 저장소를 검색해 clone 후 똑같이 설정할 수 있게 풀립니다.

받는 사람을 위한 README 5줄

5줄짜리 README가 30분의 설치 안내를 대체합니다

  • 한 줄 정의. 이 묶음이 무엇을 자동화하는지
  • 설치 안내. git clone + config.toml 병합 두 줄
  • 필요한 환경 변수. API 키 등 사용자가 미리 준비할 것
  • 첫 사용 예시. 깐 직후 바로 칠 수 있는 한 마디
  • 업데이트 방법. 새 버전을 받는 한 줄
