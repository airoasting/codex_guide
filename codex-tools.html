에이전트가 손발로 쓰는 도구를 이해합니다

1

도구의 개념

에이전트가 세상과 상호작용하는 방식

대형 언어 모델은 그 자체만으로는 텍스트를 생성하는 것 외에 아무것도 할 수 없습니다. 파일을 직접 수정하거나, 터미널 명령을 실행하거나, 외부 서비스에 데이터를 요청하려면 반드시 도구(Tool)가 필요합니다. 도구란 모델이 호출할 수 있는 함수 또는 외부 기능으로, 모델이 해당 도구를 언제·어떻게 사용할지 판단하고, 실제 실행은 호스트 환경(하네스)이 담당합니다.

Codex 에이전트에서 도구는 인간의 "손"에 해당합니다. 모델이 작업 계획을 세우면, 도구가 그 계획을 현실 세계에서 실행합니다. 도구가 없다면 에이전트는 생각만 할 수 있고 아무것도 바꾸지 못합니다.

핵심 원리

모델은 어떤 도구를 쓸지 결정하고, 하네스(실행 환경)가 그 도구를 실행합니다. 이 분리 덕분에 보안 경계와 승인 단계를 도입할 수 있습니다.

도구 없는 모델

텍스트 입력을 받아 텍스트를 출력하는 것이 전부입니다. 파일 시스템, 인터넷, 외부 서비스에 접근할 수 없습니다.

도구를 갖춘 에이전트

파일 읽기·쓰기, 명령 실행, 검색, API 호출까지 수행합니다. 모델의 판단과 도구의 실행이 결합되어 실제 작업이 완료됩니다.

2

도구의 종류

파일 접근부터 외부 API까지 네 가지 범주
📄 파일 읽기 / 쓰기 코드 파일, 설정 파일, 로그 파일을 읽고 수정합니다. 에이전트가 컨텍스트를 파악하거나 결과물을 저장하는 가장 기본적인 수단입니다. 예: read_file, write_file, list_directory
⚙️ 명령 실행 셸 명령어, 테스트 러너, 빌드 스크립트를 직접 실행합니다. 코드 변경 후 테스트를 돌리거나 패키지를 설치할 때 필수입니다. 예: bash, run_command
🔍 검색 코드베이스 내 심볼을 찾거나, 웹 검색으로 최신 정보를 가져옵니다. 에이전트가 이미 알지 못하는 내용을 실시간으로 확인할 수 있게 합니다. 예: grep, web_search
🔌 외부 API / MCP REST API 호출 또는 MCP(Model Context Protocol) 서버를 통해 외부 서비스와 연결합니다. 데이터베이스 조회, 슬랙 알림, 캘린더 업데이트 등 무한히 확장됩니다.

MCP(Model Context Protocol)란?

표준화된 도구 연결 규격

MCP는 Anthropic이 제안한 개방형 프로토콜로, 모델과 외부 도구 서버 사이의 통신 방식을 표준화합니다. MCP 서버를 한 번 구현해 두면 어떤 MCP 호환 에이전트든 동일한 방식으로 그 도구를 사용할 수 있습니다. 마치 USB가 기기 종류에 무관하게 연결되는 것과 같습니다.

MCP 서버는 파일 시스템, 데이터베이스, SaaS 서비스, 사내 시스템 등 무엇이든 감쌀 수 있으며, 에이전트는 이 서버를 통해 해당 기능을 안전하게 호출합니다.

3

권한과 안전

승인 단계와 샌드박싱으로 위험을 통제합니다

도구는 강력한 만큼 위험도 따릅니다. 파일 쓰기 도구가 잘못된 경로를 덮어쓰거나, 명령 실행 도구가 예상치 못한 프로세스를 시작할 수 있습니다. Codex 에이전트는 이를 방지하기 위해 두 가지 안전 장치를 기본으로 사용합니다.

허용 권장

읽기 전용 도구: 파일 읽기, 코드 검색, 로그 조회는 부작용이 없으므로 자유롭게 허용합니다.

제한된 쓰기: 특정 디렉터리 범위 내 파일 수정은 허용하되, 범위 밖 접근은 차단합니다.

읽기 전용 API: 외부 서비스에서 데이터를 조회만 하는 호출은 승인 없이 허용합니다.

신중하게 결정

광범위한 파일 쓰기: 루트 또는 시스템 경로 접근은 최소화하고, 필요 시 명시적 승인을 요구합니다.

무제한 명령 실행: rm -rf, 네트워크 설정 변경 등 파괴적 명령은 사전 승인 없이 차단합니다.

쓰기 API: 데이터 변경, 결제, 이메일 발송 등 되돌리기 어려운 외부 작업은 반드시 사람이 확인합니다.

🛡️
샌드박싱 원칙

Codex는 작업을 독립된 환경(샌드박스)에서 실행합니다. 에이전트가 변경을 제안하면 사람이 검토한 후 실제 코드베이스에 적용할지 결정합니다. 모든 변경은 미리보기 가능하고, 적용 전에 취소할 수 있습니다. 이 구조 덕분에 에이전트가 실수를 해도 되돌릴 수 있는 여지가 항상 남습니다.

  • 1
    도구 정의 단계에서 범위를 제한한다 도구를 등록할 때 접근 가능한 경로, 허용된 명령 패턴, 호출 가능한 API 엔드포인트를 명시적으로 제한합니다. 도구가 정의하는 범위 밖의 작업은 요청 자체가 거부됩니다.
  • 2
    파괴적 작업에는 승인 단계를 넣는다 파일 삭제, 외부 서비스 데이터 변경처럼 되돌리기 어려운 작업은 에이전트가 실행하기 전에 사람의 확인을 받도록 워크플로우를 설계합니다.
  • 3
    최소 권한 원칙을 지킨다 에이전트에게 현재 작업에 필요한 도구만 제공합니다. 불필요한 도구를 제거하면 실수로 잘못된 작업이 실행될 가능성이 줄어들고, 모델이 관련 도구에만 집중하게 됩니다.
    • 4

    도구 선택 기준

    어떤 도구를 제공할지 결정하는 네 가지 질문

    도구를 많이 줄수록 반드시 좋은 것은 아닙니다. 도구가 너무 많으면 모델이 어떤 도구를 써야 할지 혼란스러워하고, 불필요한 작업을 시도할 위험이 높아집니다. 다음 네 가지 질문으로 도구 목록을 정리하세요.

    선택 기준 체크리스트
    이 작업이 반드시 외부 실행이 필요한가?
    모델이 이미 알고 있는 정보라면 도구 없이 처리합니다. 도구는 모델이 스스로 해결할 수 없는 경우에만 씁니다.
    결과가 되돌릴 수 있는가?
    되돌릴 수 없는 작업(삭제, 전송, 결제)은 별도 승인 단계를 넣거나 도구 자체를 제공하지 않습니다.
    이 도구가 현재 작업에 실제로 필요한가?
    작업 범위와 무관한 도구는 제거합니다. 필요한 순간에만 도구를 추가하고, 작업이 끝나면 다시 제거합니다.
    도구 오류 시 어떻게 복구할 것인가?
    도구 실패가 작업 전체를 중단시키지 않도록, 재시도 로직과 폴백 경로를 하네스에 미리 정의합니다.
    MCP를 쓸 때 추가로 고려할 점

    MCP 서버를 연결하면 도구 목록이 한 번에 많이 늘어날 수 있습니다. 에이전트가 실제로 쓸 도구만 노출하도록 MCP 서버 측에서 필터링하거나, 시스템 프롬프트에서 사용할 도구를 명시적으로 안내하세요.

    도구가 실제로 어떻게 동작하는지 단계별로 봅니다

    시나리오: 버그 수정 자동화

    사용자가 "로그인 오류를 수정해 줘"라고 요청한 경우

    아래 흐름은 Codex 에이전트가 도구를 순서대로 호출하며 버그를 찾아 수정하는 과정을 보여줍니다. 각 단계에서 어떤 도구가 쓰이는지 확인하세요.

    • 1
      파일 읽기로 코드 파악 read_file 도구로 auth/login.py를 읽습니다. 모델이 코드를 분석해 오류 가능성이 있는 함수를 찾습니다. 도구: 파일 읽기
    • 2
      검색으로 관련 코드 추가 탐색 grep 도구로 validate_token 함수를 호출하는 모든 위치를 찾습니다. 버그의 영향 범위를 파악합니다. 도구: 검색
    • 3
      파일 쓰기로 수정 적용 write_file 도구로 수정된 코드를 저장합니다. 변경 내용은 샌드박스 안에 남아 있으며, 아직 실제 저장소에는 반영되지 않습니다. 도구: 파일 쓰기
    • 4
      명령 실행으로 테스트 검증 run_command 도구로 pytest tests/test_auth.py를 실행합니다. 테스트가 모두 통과하면 수정이 올바름을 확인합니다. 도구: 명령 실행
    • 5
      사람의 검토 후 병합 에이전트가 변경 사항과 테스트 결과를 요약해 보고합니다. 사람이 diff를 확인하고 승인하면 실제 코드베이스에 반영됩니다. 승인 단계
